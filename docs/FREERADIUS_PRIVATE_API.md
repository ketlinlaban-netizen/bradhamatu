# Private FreeRADIUS provisioning API contract

## Status

The Laravel application now has an mTLS client boundary for subscriber provisioning. The API service described below is **not included or deployed**: no FreeRADIUS host, VPN route, API implementation, CA, or client certificate was provided. Do not enable production provisioning until that host-side service exists and its tests pass. Until then, paid purchases stay in `activation_pending`; the application does not fall back to RouterOS writes.

## Network and TLS boundary

- Place the API on the separately managed FreeRADIUS host or an approved private service network reachable only through the authorized VPN/private route.
- Permit inbound HTTPS only from the Laravel host's approved VPN/private egress address. Do not expose RADIUS UDP ports 1812/1813 or RouterOS API ports publicly for this integration.
- Use HTTPS with a certificate valid for the exact configured API hostname. Laravel verifies the certificate chain and hostname against `RADIUS_PROVISIONING_CA_BUNDLE`, presents its client certificate/key, limits connection/request time, caps response bodies, and refuses redirects.
- Configure the exact host independently in `RADIUS_PROVISIONING_ALLOWED_HOST`. The API URL is server configuration only, not a request field; the app rejects HTTP, URL credentials, queries, fragments, or a host mismatch.
- Protect the Laravel client private key and CA bundle as runtime secrets/files outside the repository. Restrict file permissions, rotate both sides deliberately, and keep passphrases in the hosting secret store. No certificate or passphrase belongs in frontend variables or logs.
- The private API must require the expected client certificate, reject unrecognized client identities, and use request-size, rate, and schema limits of its own.

## Contract implemented by Laravel

All requests use `Content-Type: application/json`, an `Idempotency-Key`, a maximum 10-second request timeout, and an API hostname fixed in server configuration. Subscriber names are generated by Laravel; clients cannot select a URL, NAS, RADIUS command, SQL statement, or RouterOS command.

### Upsert subscriber

`PUT /v1/subscribers/{username}`

```json
{
  "service_account_id": "server-generated UUID",
  "customer_id": "server-generated UUID",
  "purchase_id": "server-generated UUID",
  "nas": {
    "id": "server-selected router UUID",
    "name": "server-selected router name",
    "ip_address": "server-selected NAS address"
  },
  "credentials": {
    "password": "transmitted only over validated mTLS"
  },
  "access_type": "hotspot",
  "bandwidth_kbps": {
    "download": 1024,
    "upload": 512
  },
  "duration_minutes": 1440,
  "expires_at": "ISO-8601 timestamp"
}
```

The `access_type` is restricted to `hotspot` or `pppoe`; bandwidth and expiry come from the server-side package snapshot. An accepted upsert returns HTTP 2xx JSON with `"status": "active"`. Implement it as an idempotent upsert keyed by the account/username and reject duplicate identity conflicts rather than creating an uncontrolled second account.

### Change password

`PATCH /v1/subscribers/{username}/password`

```json
{
  "service_account_id": "server-generated UUID",
  "password": "new customer-selected password"
}
```

Return `"status": "active"` only after the RADIUS credential has been updated. Laravel updates the customer password only after this confirmation when the customer has an active service account.

### Deactivate subscriber

`DELETE /v1/subscribers/{username}`

```json
{
  "service_account_id": "server-generated UUID",
  "reason": "Package expired"
}
```

Return `"status": "deactivated"` only after the subscriber can no longer authenticate. Laravel marks the local account expired only after this acknowledgement. Unknown users should be handled idempotently as deactivated; do not map request fields to arbitrary RADIUS operations.

## Host-side implementation guidance

The host-side API should validate mTLS identity, content type, JSON schema, account ownership/identifiers, access-type enum, integer rate limits, bounded expiry, and idempotency before any database operation. It should use a dedicated database identity restricted to the exact FreeRADIUS subscriber/attribute tables required by the selected schema. Do not grant shell access, general database administration, RADIUS client/NAS changes, or arbitrary SQL/CLI through this API.

Use the FreeRADIUS host's existing supported SQL module/schema and password-authentication policy. Restrict the API's database role, filesystem, logs, and backups because subscriber credentials may be sensitive. Store passwords only according to the chosen RADIUS authentication method and protect any cleartext credential columns as high-sensitivity data. Keep NAS shared secrets separate from subscriber passwords and outside this API response.

## cPanel/private route checklist

1. Identify the actual FreeRADIUS host, supported FreeRADIUS version, schema, and private VPN path. None has been verified in this repository.
2. Confirm the cPanel account is allowed to maintain the approved VPN route and can reach the exact API hostname and TLS port from the Laravel runtime.
3. Install the API on the private host, bind it only to its private interface, provision server CA/client certificate, and limit source addresses to the Laravel host's approved private/VPN egress.
4. Configure the host API URL, exact hostname, client certificate, private key, passphrase if applicable, and CA bundle in Laravel's server environment; never commit these values.
5. Run mocked contract tests, then an explicitly authorized non-production end-to-end test against the private host. Verify that an API timeout or TLS failure does not mark a local service active.
6. Review FreeRADIUS authentication, accounting, NAS definitions, and expiry behavior with the network operator. This client does not install FreeRADIUS, edit router NAS settings, open public router/RADIUS ports, or change network topology.
7. Roll back by disabling/removing the Laravel mTLS configuration. New paid accounts remain pending activation and existing accounts are not deleted automatically. Reconcile any in-flight activation manually with the private API operator.
